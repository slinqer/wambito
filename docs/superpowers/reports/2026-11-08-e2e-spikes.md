## Assistant secret in tokens

**Verdict: works**, with Better Auth 1.7.11 (`@better-auth/oauth-provider` 1.7.11), using one
plugin option plus a thin wrapper in front of `auth.handler`. No Better Auth patch is needed.

### What was checked

A 32-byte secret `S` (base64url, 43 characters), sent by the "web" in the consent post:

1. reaches the code exchange without being written to any table (in-memory map keyed by the
   authorization code, deleted on exchange, 10-minute expiry);
2. is appended to the refresh token as `<original>.<S>` and stripped before Better Auth sees a
   refresh, then appended again to the rotated refresh token;
3. is carried in every access token as the claim `wk` (plain base64url in the spike);
4. survives 3 consecutive refreshes (each one rotates the refresh token, each access token has `wk`,
   each access token still opens `GET /v1/categories`);
5. after the 3 refreshes, no column of any `public` table (every column of every table cast to
   `text`, so `verification`, `session`, `oauth_*`, `jwks`, `rate_limit` included) contains `S` as
   base64url, hex or standard base64. A positive control (the client id) is found in
   `oauth_client`, `oauth_consent`, `oauth_client_resource` and `oauth_refresh_token`, so the scan
   does read the rows.

Also checked: rotation is intact (reusing the first refresh token is refused with 400, and Better
Auth then tears down the token family); revocation with the suffixed refresh token works when the
wrapper strips the suffix on `/oauth2/revoke` (200, then the refresh is refused with 400); a consent
without `wk` produces exactly today's tokens (no dot, no claim).

### Better Auth hooks involved

Paths relative to `node_modules/.pnpm/@better-auth+oauth-provider@1.7.11_*/node_modules/@better-auth/oauth-provider/dist/`.

- **`customAccessTokenClaims`** (plugin option): `introspect-B-5vOvYK.mjs:239` `resolveAccessTokenClaims`,
  called at `:253`; used by the JWT mint at `:1845` (`createUserTokens`) for both
  `authorization_code` and `refresh_token` grants. It receives `{ user, scopes, resources,
  referenceId, metadata }`, no request, so `S` is read from an `AsyncLocalStorage` set by the
  wrapper. `wk` is not a reserved claim, so `stripReservedClaims` keeps it. Introspection of opaque
  tokens re-derives claims at `:2358` outside the wrapper's store, so it never sees `wk` (wanted).
- **Token endpoint**: `tokenEndpoint` `:1281`; `handleAuthorizationCodeGrant` `:1963` reads
  `ctx.body.code`; `handleRefreshTokenGrant` `:2110` reads `ctx.body.refresh_token` and calls
  `decodeRefreshToken` (`:1456`) at `:2126`, then looks the token up by its SHA-256 hash.
- **Refresh token creation**: `createRefreshToken` `:1552` stores `storeToken(hash)` of the raw
  random token and returns `encodeRefreshToken` (`:1448`). Better Auth's refresh tokens are
  `[A-Za-z]{32}` (no dot), so splitting on the last `.` is unambiguous.
- **Consent**: `authorize-CtCi8mAs.mjs:4661` (`/oauth2/consent`), body is a `z.object` of
  `accept`, `scope`, `claims`, `oauth_query`. The wrapper removes `wk` from the JSON before
  forwarding, so Better Auth never receives it; the response `{ url }` carries `code`, which keys the
  in-memory map.
- **Revoke / introspect** also decode refresh tokens: `authorize-CtCi8mAs.mjs:3724` (revoke) and
  `introspect-B-5vOvYK.mjs:2540` (introspect). The wrapper must strip the suffix there too.
- **Alternative hook (not used, worth knowing)**: `formatRefreshToken: { encrypt(token, sessionId),
  decrypt(token) }` (`:1449`, `:1462`) is applied by Better Auth itself on issue and on every decode
  (refresh, revoke, introspect). It could add and strip `.S` natively (with `S` from the same
  `AsyncLocalStorage`), removing the need to rewrite request bodies; but the response still has to
  be produced inside the store, and `auth.ts`'s own `refreshTokenUser` (suspension check, hashes
  `body.refresh_token` directly) would then see the suffixed token and need to strip it. The body
  wrapper keeps every Better Auth path, including our hook, seeing a plain token.

### How S gets from consent to the code exchange

1. The web consent page posts `{ accept: true, oauth_query, wk: <base64url S> }` to
   `/auth/oauth2/consent`.
2. The wrapper takes `wk` out, forwards the rest, reads `code` from the response's `url`, and keeps
   `code → { S, expiresAt: now + 10 min }` in a process-memory `Map`.
3. On `POST /auth/oauth2/token` with `grant_type=authorization_code`, the wrapper takes the entry
   for `code` (deleting it whatever happens), runs `auth.handler` inside
   `AsyncLocalStorage.run({ wk: S })` so `customAccessTokenClaims` adds `wk`, and appends `.S` to the
   returned `refresh_token`.
4. On `grant_type=refresh_token`, the wrapper splits `.S` off, forwards the plain token, runs the
   handler in the store with that `S`, and appends `.S` to the new refresh token.

### Risks and caveats

- **Single process.** The code → `S` map lives in memory: a restart between consent and exchange,
  or a second API instance, loses `S` (the exchange then yields tokens without `wk`; the wrapper
  should refuse instead of issuing them). Fine for today's single VPS; a multi-instance deploy
  would need sticky routing or a different carrier.
- **Revocation and introspection.** RFC 7009 answers 200 for unknown tokens, so a revoke with the
  suffixed token that is not stripped would silently revoke nothing. The wrapper must cover
  `/oauth2/revoke` and `/oauth2/introspect` (the spike covers revoke and tests it). Any future
  Better Auth endpoint that takes a refresh token needs the same.
- **Rotation and replay.** Rotation is unchanged (`refreshTokenReuseInterval` is 0): a reused
  refresh token kills the family, and the assistant must reconnect through the web (passkey) to get
  `S` again. Concurrent refreshes by a client therefore cost a reconnect, as today.
- **Token length.** Spike: access token 741 characters with a plain `wk` (about +50), refresh token
  76 (32 + 1 + 43). A JWE-wrapped `wk` adds roughly 200–250 characters; still far below header
  limits.
- **Who holds `S`.** The refresh token carries `S` in the clear to the assistant's company (by
  design, spec section 9); only the access token's copy is encrypted to the MCP. `S` alone opens
  nothing without the server-held `assistant` wrap.
- **Logs.** `S` travels only in POST bodies and response bodies; nothing in the API logs bodies
  today, and the wrapper must not either. Not verified beyond reading the config.
- **Spike shortcuts.** The plugin option was injected with `vi.mock` around `oauthProvider` and the
  wrapper was installed by replacing the test app's `fetch`; production code would set both
  directly (files above).
