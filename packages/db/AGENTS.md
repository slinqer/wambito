# packages/db (`@wambito/db`)

Drizzle schema, SQL migrations and row-level security for Postgres.

## Entry points

- `src/schema/domain.ts` (app tables), `src/schema/auth.ts` (Better Auth tables, generated by
  `pnpm --filter @wambito/api auth:generate`).
- `drizzle/*.sql` + `drizzle/meta`: migrations; `drizzle/0001_rls.sql` holds the RLS policies.
- `src/migrate.ts` (`runMigrations`), `src/bootstrap.ts` (`ensureAppRole`, `grantAppRole`, `prepareDatabase`, `APP_ROLE`, `databaseUrl`),
  `src/client.ts`, `src/orm.ts`, `src/testing.ts` (test Postgres).
- Scripts: `pnpm --filter @wambito/db generate` (drizzle-kit), `migrate`, `bootstrap` (`--role-only`;
  `--grant-only DB` grants the app role on another database, for a restore drill).
- `testing.ts` `RESTORE_FLAGS`: the pg_restore flags `deploy/personal/restore.sh` and `backup.sh` use.

## Rules

- Migrations run as the admin/owner role, never as the runtime role (`APP_ROLE`,
  `NOSUPERUSER NOBYPASSRLS`): every user table needs RLS, except the ones read before the user is
  known (`session`, `passkey`, `recovery_verifiers`, `signin_requests`, `activity_daily`,
  `ended_sessions`, `deleted_users`). Its grants are not in migrations: they
  live in `grantAppRole` (bootstrap), which `prepareDatabase` runs after the migrations.
- Add migrations with drizzle-kit; never edit an applied one (the one exception: `0001`'s grants
  moved to the bootstrap in part 2b).
- `admin_audit` is append-only: the app role has no UPDATE/DELETE on it, `grantAppRole` revokes them
  (only when the table exists, so a restore drill on a dump from before 0008 still grants).
- `records`, `key_wraps`, `pairing_requests` (0010) are the end-to-end encrypted store: `body`/`wrapped`
  are opaque `bytea` (the `bytea` custom type gives `Uint8Array`); `records.version` comes from
  `records_version_seq`, raised on every write with `set version = nextval('records_version_seq')`.
- `0011` adds the pairing `commitment`/`approver_key`/`key_v` columns, `key_wraps.attestation`
  (device wraps need it, 32 bytes) and `record_purges` (`user_id` primary key, `through_version`:
  the highest purged tombstone version, so older clients resync), with RLS like `records`. Its device-attestation CHECK fails on a dev database that holds stage-1
  device wraps without an attestation: run `delete from key_wraps where kind='device'` before
  migrating.
- `0012` adds `key_links` (`user_id`, `key_v` >= 2 primary key, `link` 60 bytes: the previous data key sealed under the new one, one per rotation; RLS like `records`) and `key_wraps.session_id` (the Better Auth session that registered a device wrap, `on delete set null`, device wraps only).
- `0013` adds `user.encryption` (text not null default `plain`, CHECK `plain`/`encrypted`) and `user.platform` (text null, CHECK `android`/`ios`/`web`). The CHECKs are in the SQL only (`auth.ts` is generated).
- `0014` (custom, data only) empties `rate_limit` and nulls `session.ip_address`: no IP address is stored any more (rate limits live in API memory). The columns stay (generated by Better Auth).
- `0015` adds `session.lifetime` (text not null default `standard`, CHECK `standard`/`long`/`short`; `apps/api/src/services/sessions.ts`). The CHECK is in the SQL only.
- `0016` adds `recovery_verifiers` (`user_id` primary key → `user` on delete cascade, `lookup_hash` unique and `auth_hash`, both `bytea` CHECK 32 bytes: SHA-256 of the recovery key's lookup and auth). No row-level security (plan decision 4): it is read by `lookup_hash` before the user is known, like `session` and `passkey`; every statement filters on the user id or the lookup hash.
- `0017` adds `signin_requests` (the web's sign-in through the phone, `apps/api/src/services/signin.ts`): `id` uuid, `code` unique, `commitment` and `poll_hash` (SHA-256 of the poll secret) `bytea` CHECK 32 bytes, `label` (CHECK 1–64 characters), `remember`, `user_id` null until the phone approves (→ `user` on delete cascade), `approver_key`/`public_key` (CHECK 32 bytes), `key_v`, `sealed`, `expires_at`. No row-level security (plan decision 4): it is read before the user is known, by `code` or by `id` and `poll_hash`; every statement filters on the request id or the code.
- `0018` adds `activity_daily` (`apps/api/src/services/activity.ts`): `day` date, `platform`, `app_version` (`''` when none), `cohort_week` date (the Monday of the user's `created_at`), `has_email`, `count`; primary key over the first five. No user id column and no row-level security (plan decision 4): it counts people per day and keeps no per-person history. Also `user.app_version` and `user.last_seen_day` (text `YYYY-MM-DD`), Better Auth fields.
- `0019` adds `ended_sessions` (`session_hash` primary key, SHA-256 of the session token; `reason` CHECK `device_removed`; `ended_at`, purged after 90 days) and `deleted_users` (`user_hash` primary key, SHA-256 of a user id the inactivity cleanup deleted; `deleted_at`; kept), both `bytea` CHECK 32 bytes (`apps/api/src/services/ended.ts`). No user id column and no row-level security (plan decision 4): both are read before the user is known.
- `0020` replaces the `records` CHECK `records_deleted_body` with `records_live_body` (`deleted or body is not null`): a tombstone may keep its sealed body until the 180-day purge.
- In production `docker compose run --rm migrate` (`deploy/personal/up.sh`) runs bootstrap +
  migrations.
